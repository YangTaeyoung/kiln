# Kiln 0.1.12 verification

This corrective release addresses local-network permission discoverability and
Claude browser sign-in losing the macOS login Keychain. Publication evidence is
recorded separately below after all release gates pass.

## Confirmed findings and fixes

- The previous bundle omitted `NSLocalNetworkUsageDescription`. Both GUI and
  menu companion now include native descriptions in English, Korean, Japanese
  and Simplified Chinese, configured before signing.
- The companion was a renamed copy of the GUI executable under a different
  bundle ID. It now has its own entry point and executable. Bundle preparation
  and final verification reject missing/colliding build UUIDs and mismatched
  architectures. This follows [Apple TN3178](https://developer.apple.com/documentation/technotes/tn3178-checking-for-and-resolving-build-uuid-problems).
- Settings includes a macOS 15+ explicit request using the documented best-effort
  UDP-connect approach, without sending packets or querying user hosts. It never
  treats connection results as an authorization verdict. See the
  [local-network guide](../local-network.md) and [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).
- A read-only experiment reproduced the Keychain failure: `security
  default-keychain -d user` succeeded with the real home, but failed with a fresh
  temporary `HOME`; the temporary environment's Keychain search list was empty.
  No Keychain items, search lists or defaults were modified. Claude now keeps
  the real home while isolating `CLAUDE_CONFIG_DIR`. File/metadata reads remain
  disposable to avoid attaching an existing account's identity to a new token.
  References: [Claude account isolation](https://code.claude.com/docs/en/authentication#log-in-with-multiple-accounts),
  [Apple Keychain home lookup](https://github.com/apple-oss-distributions/Security/blob/main/OSX/libsecurity_keychain/lib/StorageManager.cpp#L2063-L2091).
- The official CLI's private-file fallback is consumed before a Keychain lookup.
  Failed Keychain writes are no longer treated as optional missing items or
  successful profile saves.
- Both updater-test entry points initialize the same compiled private root
  before accessing settings or sockets. Fixture preparation rejects a production,
  stale or differently isolated companion.

## Local source and UI verification

- Application: 184 unit tests passed; five opt-in tests ignored by the default run.
- GUI/session integration: 40 tests passed; one opt-in screenshot test ignored.
- Accounts: 55 unit/UI tests passed, including CLI child cleanup, actual-home
  preservation, isolated fallback/metadata and failed-write classification.
- Privacy bundle metadata and UUID guards: four isolated Python regressions passed.
- Localization checker: eight regressions passed; 2,007 messages and 1,899 literal
  UI keys validated in four languages.
- Privacy controls: 64 rendered fixtures across four languages, light/dark,
  360/680-point windows, four notices and 130% scale. Request/settings callbacks
  are synthetic; these fixtures do not invoke macOS permissions.
- Independent hostile source reviewers passed the privacy and authentication
  fixes. The first privacy review caught missing updater-helper isolation; the
  accounts suite exposed a cleanup fixture that inferred the temporary root
  from HOME. Both were corrected, retaining child/session cleanup assertions.
- Independent visual review inspected six representative privacy captures and
  passed hierarchy, wrapping and neutral-result wording. This is rendered-fixture
  evidence, not a native window/permission observation.
- Both debug updater-test binaries built and reported the same compiled private
  root with no inherited Kiln environment. Only version/root commands were run;
  no fixture GUI, status menu or real session connection was started.

## Boundaries

Actual permission prompts, application attribution for detached terminal children,
Finder/menu-companion opening, an upgraded retained daemon and the reported
`kubectl get nodes` connection require verification on the affected Mac after
updating. The usage-description/UUID defects are verified; their causal role in
that specific connection failure is not established. Actual browser OAuth success
after this fix is also unobserved. No real authentication is performed by tests.

The existing Keychain CLI writer still passes secrets as process arguments.
That separate security hardening is not claimed as fixed here. Do not substitute
an unverified `security -i` implementation: Apple's tool has a 4,096-byte line
buffer and large credential payloads need explicit handling and regression tests.
Reference: [Apple Security tool](https://github.com/apple-oss-distributions/Security/blob/main/SecurityTool/macOS/security.c).

No installed app is replaced directly and no user terminal/daemon is stopped.
The owner chose to use the official automatic update feed.
