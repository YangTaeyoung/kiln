# Kiln 0.1.5 verification

## Behavior and review

Running shell and agent tasks lead workspace history and recent work. Both use
one activity classifier; explicit waiting, completed and failed states take
precedence over unfinished shell commands. An idle agent's launch command cannot
mark it as busy or replace its task title. Recent work freezes row order while
open and retains selection by pane identity.

Panel headers expose split-right, split-down and close with independent 26pt hit
targets. They act on their own pane, including an inactive split. Secondary actions
move to the menu at narrow widths; extremely narrow manual splits hide identity
before overlapping controls and retain accessible overflow actions.

The running-process confirmation offers **Don’t ask again**, with its scope and
re-enable path visible. Only affirmative confirmation writes the existing setting.
Cancel and Escape leave it unchanged. Unsaved files and launch requests keep
independent warnings. Closing the last panel creates an empty terminal instead
of closing the application.

Missing interface translations are covered across Korean, English, Japanese and
Simplified Chinese. New activity notifications persist an event type and translate
when displayed; user notification titles and terminal output remain unchanged.
Old notifications without event metadata retain their original text. Generated
workspace context follows the selected language without rewriting saved requests.
The coverage checker scans production code after inline test modules and has
lexer regressions for strings, comments and conditional test-only items.

## Installed-app observation boundary

The installed app was still **0.1.4** at the initial release observation. Before the update, all
five original session IDs and shell PIDs remain present and alive. Screen and
accessibility observations succeeded, but native input was intermittently blocked
by `The user changed '/Applications/Kiln.app'` and a ScreenCaptureKit stream error.
Opening Settings was observed once; subsequent update navigation was not reliable.
No update/relaunch or installed 0.1.5 header appearance is claimed.

The owner has been asked to use Settings → About → Check for Updates and install
0.1.5. After that, recheck the installed app/helper versions, live daemon status,
original session IDs/PIDs and visible header controls before declaring the live
upgrade complete. Take a fresh private baseline if resuming on another machine or
session. Renderer/PTY tests above establish implementation behavior, not this
pending installed-app observation.

### Follow-up: installed 0.1.5 and missing menu icon

On October 5, 2026 (16:24 KST), the installed bundle and CLI report **0.1.5**.
All five session IDs and shell PIDs recorded before the update are still present
and alive. This verifies installed version and session survival, not every visible
control or the owner's update steps.

The owner reports that the menu-bar icon is absent. The installed companion was
running from `/Applications/Kiln.app`; its icon asset matches the source, contains
an opaque symbol and was open in the companion process. Source and design/DX
review found no deleted icon or empty mask. These checks do not prove that AppKit
is displaying the status item, and the root cause remains unconfirmed.

Only that companion was terminated and relaunched through LaunchServices from
the installed nested app. The daemon, GUI and all five original sessions remained
alive. Owner confirmation of the restored menu icon is pending. Do not describe
this restart as a permanent fix or attribute the defect to update-time `exec()`
without further evidence.
